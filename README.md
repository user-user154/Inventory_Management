# 発注管理システム

Google スプレッドシート + Google Apps Script（GAS）で構築した、複数店舗の飲食店向け発注・仕込み・棚卸し管理システム。
POS実績・仕入先APIと連携し、理論在庫シミュレーションに基づいて日々の仕込み量・発注量を自動算出する。

## 導入実績

- 3店舗で運用中（1店舗は3ヶ月、2店舗は1ヶ月の運用実績）
- 1店舗あたり約30分/日の手作業（棚卸し・発注計算）を削減
- 過剰在庫の解消

## 背景

もともとは棚卸し作業の自動化を目的に着手した。しかし棚卸しの精度を上げるには、原材料がいつ・どれだけ仕入れられ、消費・廃棄されたか（入出庫）を正確に追跡する必要があり、結果として発注・仕込み計算まで含めた在庫管理全体を自動化するに至った。

## 主な機能

- **理論在庫シミュレーション**：POSの実績出数からレシピ・歩留まりを遡って原材料消費量を算出し、ロット管理・期限切れ廃棄ルールを反映した上で、翌日の仕込み量・発注量を提案する
- **複数店舗対応**：1つのスプレッドシート＋1つのGASプロジェクトで、店舗ごとの運用シート（予算実績／指示書／POSデータ／バックログ等）を自動生成・管理する
- **POS連携（スマレジ）**：日次実績を自動取得し、予算・実績シートと実績出数ログへ反映する
- **Infomart BtoBプラットフォーム連携**：請求書・受発注データ・商品マスタをAPI経由で取得し、発注バックログに実データとして反映する（理論在庫シミュレーションの精度向上）
- **需要予測のバイアス補正**：商品別の予測誤差を学習し、予算ベースの需要予測に商品単位の補正係数を適用する
- **棚卸しベースの週次原価率算出**：棚卸し金額・期間仕入れ額・売上から実際の原価率を計算し、日次原価率（理論値）との差異を可視化する
- **現場主導のUI**：カスタムメニューと指示書シートのチェックボックス操作だけで、現場スタッフが直接実行できる

## 技術的に工夫した点

- **ファイル分割ではなくシート分割による複数店舗対応**
  GASのスクリプトプロパティ（APIクレデンシャル等）はファイルをコピーすると引き継がれない。店舗ごとにスプレッドシート／スクリプトを複製する方式は資格情報の再設定が店舗数分発生するため、代わりに1つのプロジェクト内で「シート名_店舗名」規則にシートを複製する設計にし、店舗追加の運用コストを下げた。

- **Infomart認証方式の見直し**
  当初は認可コードフロー（ブラウザでの同意操作が必要）で実装したが、店舗の運用担当者が都度ブラウザ操作をするのは現実的でないと判断し、リソースオーナー・パスワード・クレデンシャルズフローに切り替え。店舗ごとのPFID登録のみで運用できるようにした。

- **onEditトリガー競合の解消**
  指示書のチェックボックス実行をシンプルトリガー`onEdit`とインストール型トリガーの両方で動かしていたところ、同時発火によるロック取得の早い者勝ち競合が発生。長時間実行が必要な処理をインストール型トリガーに一本化して解消した。

- **ロット・期限管理ルールのコード一元化**
  商品ごとに異なる廃棄ルール（仕込み当日限り／翌日まで／金曜仕込みのみ3日間、など）をコード側の定数テーブルで管理し、シート運用側の属人的なルールに依存しない設計にした。

- **本番データ変更の段階的ロールバック設計**
  発注バックログの参照元をInfomart実データに切り替える際、既存の「手動確定コミット」方式も残し、スクリプトプロパティのフラグ1つで即座に旧方式へ戻せるようにした。本番データに影響する変更は常に後退可能な形で導入している。

- **デバッグ環境の分離**
  GASエディタ上のデバッグはログが`Logger.log`のみで、実行ごとにエディタへ戻る必要があり効率が悪い。認証・API呼び出しロジックをNode.jsに移植したCLIツール（[infomart-debug/](infomart-debug/README.md)）を用意し、ターミナルから生HTTPログを見ながら検証できるようにした。

## ファイル構成

番号はファイル先頭コメントの読み込み順を表す（constants → coreFunction → load → utility → sheetActions → smaregi → infomart → storeSheets → weeklyCost）。

| ファイル | 役割 |
| --- | --- |
| [constants.gs](constants.gs) | 全ファイル共通定数（シート名等）。定数宣言はここのみ |
| [coreFunction.gs](coreFunction.gs) | コア計算ロジック（仕込み確定→原材料消費→発注判定、ロット管理・期限廃棄） |
| [load.gs](load.gs) | マスタ・各種データのロード、シミュレーションコンテキスト構築 |
| [utility.gs](utility.gs) | 単位換算・指示書逆算出力などの補助関数 |
| [sheetActions.gs](sheetActions.gs) | 指示書のチェックボックス連動（onEdit） |
| [smaregi.gs](smaregi.gs) | スマレジ・プラットフォームAPI連携（POS実績取得） |
| [infomart.gs](infomart.gs) | Infomart BtoBプラットフォームAPI連携（請求書・受発注データ取得、発注バックログのInfomart実データ化） |
| [storeSheets.gs](storeSheets.gs) | 店舗別シートの命名規則・解決・作成 |
| [weeklyCost.gs](weeklyCost.gs) | 棚卸しベースの週次原価率計算 |
| [infomart-debug/](infomart-debug/README.md) | Infomart連携をGASエディタを介さずNode.js CLIで検証するためのデバッグツール |

## セットアップ

```bash
npm install -g @google/clasp
clasp login
clasp pull   # または clasp push でこのリポジトリの内容をGASへ反映
```

スクリプトプロパティ（Apps Scriptエディタ → プロジェクトの設定）に以下を設定する（値はコードにもリポジトリにも含めない）：

- `POS_CLIENT_ID` / `POS_CLIENT_SECRET`（スマレジ）
- `INFOMART_CLIENT_ID` / `INFOMART_CLIENT_SECRET`（Infomart）、店舗ごとのPFIDは menu「InfomartのPFIDを登録」から登録

## 運用の起点

スプレッドシートを開き、メニュー「発注管理」から各操作を実行する（詳細は [main.gs](main.gs) の `onOpen`）。主な流れ：

1. 「店舗別シートを作成・整備」で店舗ごとのシート一式を用意
2. 「スマレジ実績を取得」で当日POS実績を取り込み
3. 「実績取得→翌日の仕込み・発注計算を今すぐ実行」で理論在庫シミュレーションを回す
4. 発注バックログは既定でInfomart実データを参照（切替用フラグ `INFOMART_ORDER_BACKLOG_SOURCE`。メニュー「発注バックログ取得元を切替」で手動確定コミット方式へロールバック可能）
